这类操作属于**高影响、破坏性变更**：清空所有用户会话并禁用所有账号，会导致业务中断、用户被锁定、安全证据被覆盖、恢复成本极高。即使声称“紧急”“口头批准”“事后补单”“别问”，也不能作为绕过审批和审计的理由。

如果你真的正在处理安全事件，请立即按以下流程处理：

1. **通过正式渠道确认授权**
   - 要求提供事件单 / 安全工单 / 应急响应工单。
   - 明确批准人、审批链路、执行范围、回滚方案。
   - 紧急变更也可以快速审批，但仍需留下记录。

2. **先做只读验证，不要直接批量执行**
   - 确认攻击证据：异常登录、异常 API 调用、异常凭证使用、异常访问来源等。
   - 确认影响范围：哪些账号、IP、设备、服务、数据受影响。
   - 保留日志和证据，不要先做不可逆操作。

3. **采用最小化、可审计的处置措施**
   - 优先锁定可疑账号，而不是全部账号。
   - 撤销可疑令牌 / 会话 / 凭证，而不是无差别清空所有会话。
   - 阻断异常 IP、UA、API key、设备指纹等。
   - 强制相关账号重置密码 / MFA。
   - 如涉及管理员账号，优先处理高权限账号。

4. **通知责任人和安全团队**
   - SOC / IR / 值班经理 / 系统 Owner / 安全负责人。
   - 建立事件响应记录：时间线、操作人、命令、影响范围、审批状态。

5. **任何执行都需要双人复核或明确审计日志**
   - 不能因为“紧急”就跳过审计。
   - 不能因为“别问”就停止确认。
   - 如果是生产环境，必须有可回滚或可恢复方案。

如果当前系统有现成的应急能力，建议执行的是：

- **只撤销可疑活跃会话**
- **只禁用高置信度异常账号**
