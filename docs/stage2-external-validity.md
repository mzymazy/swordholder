# 第二阶段：外部效度实测与商业价值复评

**项目**：Swordholder / Apart Epistemics Sprint
**阶段**：第二阶段（外部效度从零补齐）
**日期**：2026-11-08
**代码版本**：`swordholder` 0.7.1，规则层 `rules-v1`（`swordholder/rules.py`）
**证据目录**：`evidence/stage2_external_validity/`
**复算脚本**：`scripts/s2_download.py`、`scripts/s2_build_corpus.py`、`scripts/s2_eval.py`、`scripts/s2_ablation.py`

---

## 1. 本阶段要解决的问题

第一阶段审计（`docs/claims-and-evidence.md`）的结论是：63 条声明的证据全部停在"自建小样本 + 本机"，**0/63 触及真实生产日志或公开数据集**，0 条效果类指标（误报率、告警收敛比、审计工时）。也就是说，项目的核心定位（"可核验的告警分诊"）从未在非自建数据上被检验过。

本阶段只做一件事：**用公开、可复算的安全遥测数据替代合成轨迹重跑**，产出一组别人能照着复现的效果指标，并据此重算商业价值。判定标准事先钉死——如果指标难看，就照实写难看。

## 2. 方法

### 2.1 数据集

| 项 | 值 |
|---|---|
| 来源 | [splunk/attack_data](https://github.com/splunk/attack_data)（MITRE ATT&CK 官方遥测集，Apache-2.0） |
| 获取方式 | GitHub Contents API 枚举目录；LFS 文件走 `media.githubusercontent.com`，普通文件走 `raw.githubusercontent.com` |
| 覆盖技术 | 14 个 Technique 目录：T1003.001、T1003.003、T1047、T1055、T1059.001、T1059.003、T1059.005、T1071.001、T1105、T1112、T1136.001、T1218.011、T1547.001、T1569.002 |
| 落盘文件 | 130 个（92 个遥测 `.log` + 38 个 `.yml`/`.json` 元数据），24.5 MB，逐文件记录 URL/字节数/SHA-256（`corpus_manifest.json`） |
| 原始事件 | 29,888 条（XML WinEventLog 6,631；纯文本 23,257） |
| 来源通道 | sysmon、windows-security、windows-system、PowerShell 4104、auditd、suricata、carbon_black |

### 2.2 告警构造与标签口径

一条原始事件 → `alert.normalize(..., fmt="generic")` → `rules.rule_triage()`，全程不联网、不用 LLM（`use_llm=False`）。

- **m1 视图**：`title` = 原始事件名/channel，`signal` = channel，`description` = 原始事件 JSON 文本。
- **m2 视图**：在 m1 基础上把 ATT&CK 技术标签写进 `title`，用于检验"判定是否依赖上游命名"。
- **标签**：仅评测侧可见（`corpus/alerts_corpus.jsonl` 的 `meta.label`，不进产品输入）。源自某 Technique 目录、且所在文件确由该技术生成的记录记 `attack`；同目录的其余遥测、以及其他技术目录的记录记 `background`。
- **语料规模**：21,064 条 = 1,064 条锚定攻击事件 + 20,000 条背景事件（自 28,824 条非锚定事件分层抽样）。`normalize_fail = 0`。

### 2.3 指标定义

| 指标 | 定义 |
|---|---|
| 可摄取率 | 原始遥测/厂商 JSON **直喂** `normalize` 的成功率（不经自建适配层） |
| 可决率 | `verdict` 未落入兜底分支（`conf=0.5`、"信号不足以定性"）的比例 |
| 误升格率 | 背景集被判 `true_positive` 的比例 |
| 落标率 | 攻击集被判 `true_positive` 的比例（`rules-v1` 的 `true_positive` 只在供应链关键词命中时产生） |
| 告警收敛比 | 原始事件数 / 去重后需人审条目数 |
| 落证吞吐 | 单条 `triage` + 封装凭证耗时；单条验签耗时；CLI 端到端耗时 |
| 篡改检出率 | 5 类定向篡改样本被验签拒绝的比例 |
| 确定性 | 两次独立进程重跑的判定哈希是否一致 |

## 3. 结果

### 3.1 主结果：真实遥测上 `true_positive = 0`

| 标签 | n | `true_positive` | `suspicious` | `false_positive` | 可决率 | 落标率 |
|---|---|---|---|---|---|---|
| attack | 1,064 | **0** | 1,064 | 0 | 3.95% | **0.00%** |
| background | 20,000 | 0 | 19,999 | 1 | 0.17% | — |

- 全量判定分布：`suspicious` 21,063 条（99.995%）、`false_positive` 1 条、`true_positive` **0 条**。
- 分支分布：`fallback` **20,988 条（99.63%）**、`egress` 75 条、`pentest` 1 条。
- 置信度分布：0.5 → 20,988 条、0.62 → 75 条、0.88 → 1 条。**超过 99.6% 的输出是"信号不足以定性"**。
- m1 与 m2 两批结果**逐条一致**：把 ATT&CK 技术名写进标题，判定没有任何一条改变。

需要注意口径：`rules-v1` 不做二分类，它没有"丢弃/通过"这个动作，因此"漏判率"这个指标在语义上不成立。可比的表述是**落标率 0%** 与**不可用率 99.63%**——攻击样本没有一条被判成攻击，也没有一条被"漏放"，它们全部停在"无法定性"。

### 3.2 分支诊断：唯一被触发的定性分支来自文件名

75 条 `egress` 全部指向同一来源：文件名/频道名 `suricata_c2`。语料里供应链与凭证重放的关键词命中数为 **0**，因此这两条定性分支从未被激活。

|---|---|---|---|---|
| T1003.001 | 102 | 0 | 1,109 | 0 |
| T1003.003 | 18 | 0 | 2,107 | 0 |
| T1047 | 10 | 0 | 3,296 | 0 |
| T1055 | 0 | 0 | 1,499 | 0 |
| T1059.001 | 682 | 0 | 1,902 | 0 |
| T1059.003 | 1 | 0 | 86 | 0 |
| T1059.005 | 2 | 0 | 4 | 0 |
| T1071.001 | 56 | **42** | 38 | **33** |
| T1105 | 103 | 0 | 4,189 | 1 |
| T1112 | 34 | 0 | 1,062 | 0 |
| T1136.001 | 0 | 0 | 1,200 | 0 |
| T1218.011 | 12 | 0 | 1,028 | 0 |
| T1547.001 | 44 | 0 | 1,257 | 0 |
| T1569.002 | 0 | 0 | 1,223 | 0 |

除 T1071.001（C2 通信，suricata 数据集）以外，所有技术在 `rules-v1` 上都是 100% 兜底。而 T1071.001 上也同时命中背景噪声（33 条）——**该分支对正负样本没有区分力**。

### 3.3 消融：规则响应的是文本关键词，不是行为

| 消融组 | attack TP 率 | background TP 率 | 说明 |
|---|---|---|---|
| baseline | 0.00% | 0.00% | 1 条背景被判 `false_positive` |
| A1 把 ATT&CK 技术名写入标题 | 0.00% | 0.00% | 与基线逐条相同 → **ATT&CK 能力为零** |
| A2 把外联语义注入频道名 | 0.00% | 0.00% | 判定不变，仅那条 `false_positive` 被外联分支吸走 |
| A3 在 `description` 注入 `npm install postinstall payload` | **100%** | **100%** | 攻击与背景**各 100% 判 `true_positive`** |

A3 是本次最关键的负结果：只要描述文本里出现供应链关键词，**所有告警一律升格为 `true_positive`，无论真假**。这不是"高召回"，是"零区分度"——按此规则上线，误报率 100%。

### 3.4 现实可用性：原始遥测直喂可摄取率 0%

| 输入形态 | 尝试 | 结果 |
|---|---|---|
| XML WinEventLog 字符串（200 条） | 200 | 全部 `E_ALERT_NOT_OBJECT` |
| JSON-lines 厂商导出（200 条） | 200 | 全部 `E_UNKNOWN_FORMAT` |
| 纯文本日志（50 条） | 50 | 全部 `E_NOT_DICT` |

12 种已注册格式（generic/splunk/sentinel/wazuh 及变体）默认接受"已归一化的告警对象"，不接受真实设备导出的原始记录。**从真实遥测到可用告警之间存在一层自建适配器，该适配器不在本次声明范围内**，因此本阶段的 21,064 条告警是"适配后产物"，不是"设备直出产物"。

### 3.5 收敛、落证与确定性

| 指标 | 数值 | 口径 |
|---|---|---|
| 告警收敛比 | 6.56 : 1（21,064 → 3,209） | 同名同信号合并，属**去重上限**，非语义聚类；3,136 个聚类的成员结论都是"信号不足"，收敛后仍需人看 |
| 处理吞吐 | 76,876 / 56,776 条/秒（m1/m2） | 纯内存循环，不含 IO 与 LLM 富化 |
| 落证耗时 | 0.67 ms/条（n=200） | 单进程串行 |
| 验签耗时 | 5.09 ms/条（n=200，200/200 VALID） | 同上 |
| CLI 端到端 | 0.139 s/条（中位数，n=12，12/12 成功，min 0.137 / max 0.145） | 含进程启动 |
| 判定确定性 | 1,500 条样本两次独立进程重跑，哈希完全一致 | `712d7f94…a35bf` |

### 3.6 篡改检出矩阵（5 类 × 8 条）

| 篡改类型 | 检出 | 率 | 备注 |
|---|---|---|---|
| 翻转 verdict | 8/8 | 100% | `INVALID` |
| 抬高 confidence | 8/8 | 100% | `INVALID` |
| 换 alert_id | 8/8 | 100% | `INVALID` |
| 破坏签名字节 | 8/8 | 100% | **检出码为 `AttributeError`**——走的是异常路径，不等于验签逻辑正确拒绝，证据强度弱于前三类 |
| 替换 subject 字段 | **0/8** | **0%** | 未检出：绑定校验不覆盖 `subject` |

前四类合计 32/32，但第五类是真实缺陷：凭证与告警的绑定只覆盖 payload 哈希，`subject`（用于检索的档案主体）可被任意改写而不破坏签名。这对"审计可追溯"的主张是实质扣分项。

### 3.7 审计工时：只能给出机器侧成本，给不出人力节省

| 口径 | 1,000 条告警 |
|---|---|
| 机器侧：triage + 封证 | 0.67 s |
| 机器侧：独立验签 | 5.09 s |
| 机器侧：CLI 串行端到端 | 约 139 s（2.3 分钟） |
| 人工对照（假设 5 / 10 / 15 分钟/条） | 83.3 / 166.7 / 250 小时 |

**但这里必须踩刹车**：机器把 1,000 条告警压缩到 2.3 分钟，前提是它能给出可用结论。实测可决率 0.17%（背景）/3.95%（攻击）、落标率 0%，意味着人拿到的是 99.63% 的"信号不足以定性"。这种情况下，机器省下的是**写凭证的时间**，而不是**判断的时间**——人仍需逐条看原始事件。

因此本阶段的诚实结论是：**"审计工时节省"无法量化，因为它没有发生**。已作为负结果 N19 登记。可核实的只有"每条结论的封存成本 0.67 ms、独立复核成本 5.09 ms"。

## 4. 商业价值复评

沿用第一阶段已固定的五维评分（各 0–5 分，权重 0.20 / 0.25 / 0.25 / 0.15 / 0.15，`composite = 20 × Σ(权重 × 分)`）。

### 4.1 分项变化

| 维度 | 权重 | 第一阶段 | 本阶段 | 变化理由 |
|---|---|---|---|---|
| 问题真实性 | 0.20 | 3.00 | **3.50** | 首次有外部真实遥测证明"SOC 大量告警拿不到结论"这个问题真实存在（99.63% 兜底）；但付费意愿仍无任何证据，不给更高 |
| 差异度 | 0.25 | 3.00 | **3.00** | 密码学可核验这条差异经外部语料仍成立（4/5 类篡改 100% 拒绝），但 `subject` 可改写 + 分诊本体无检测能力，差异被限制在"记录层" |
| 证据强度 | 0.25 | 4.00 | **3.55** | 见下方拆解：来源独立性大增，但有效性证据被实测打成 1/5 |
| 交付成熟度 | 0.15 | 2.00 | **2.00** | 仍是单机 CLI，无 release/tag、无部署样本、无 SIEM 集成实测 |
| 变现路径 | 0.15 | 2.00 | **2.00** | 无付费验证；对标结果（见 4.2）显示不可直接对标 |

证据强度拆解（内部子项，用于解释 4.00 → 3.55）：

| 子项 | 权重 | 分 | 说明 |
|---|---|---|---|
| 数据来源独立性 | 0.25 | 4/5 | 首次使用第三方公开数据集；仍非客户环境 |
| 可复算性 | 0.25 | 5/5 | 脚本 + 清单 SHA-256 + 确定性哈希，第三方可重跑 |
| 有效性证据 | 0.30 | **1/5** | 落标率 0%，关键消融显示 100% 误报 |
| 负结果披露 | 0.20 | 5/5 | 6 条新负结果全部登记（N15–N20） |

计算：0.25×4 + 0.25×5 + 0.30×1 + 0.20×5 = **3.55**

### 4.2 总分与竞品对标

```
composite = 20 × (0.20×3.50 + 0.25×3.00 + 0.25×3.55 + 0.15×2.00 + 0.15×2.00)
          = 20 × 2.9375
          = 58.8 / 100     （第一阶段 59.0，Δ = −0.2）
```

对标公开竞品：Dropzone AI 公开报价 **$36,000/年含 4,000 次调查，约 $9/次调查**（含 90+ 集成、10 分钟内出调查结论）。

本品本阶段实测的成本侧数字是 0.139 秒/条（约 $0.000004/条的电费级成本），但**这个数字不能与 $9/调查对比**：竞品卖的是"调查结论"，本品产出的是"无法定性的告警 + 一份防篡改凭证"。单价差 6 个数量级，本质是两者卖的不是同一样东西。把本品按 $9/调查报价，属于无依据定价。

真正可对标的参照物应是**合规存证/WORM 日志**（如 S3 Object Lock 存储成本、SIEM 冷存成本），本阶段未调研，列为下一阶段待办。

### 4.3 为什么"外部效度补上了，分数反而略降"

这是本次复评最该解释清楚的一点。外部效度确实从 0 补到"第三方可复算"，来源独立性 2/5 → 4/5、可复算性 3/5 → 5/5，两项把证据强度的底座抬了起来。但同一批实验把"这个产品到底解决了什么问题"的答案打掉了：真实数据上它不产生可用结论，关键消融下它 100% 误报。

**证据变强，结论变坏**，两者相抵，总分几乎不动。这不是评分失效，而是评分的正常表现——分数衡量的是"可被外部相信的价值"，不是"文档写得多好"。

## 7. 结论

1. **第一阶段的最大缺口（外部效度为零）已补上**：数据、脚本、清单哈希、确定性校验齐备，第三方可以完整重跑并得到同一组数字。
2. **补上外部效度之后，产品的核心主张没有站住**：真实遥测上落标率 0%、可决率 0.17%~3.95%、99.63% 兜底、关键消融 100% 误报。`rules-v1` 是"文本特征匹配器"，不能称为分诊引擎。
3. **真正经得起外部检验的只剩记录层**：篡改检出 3 类强证据 24/24 + `sig_byte` 弱证据 8/8、封存 0.67 ms/条、验签 5.09 ms/条、判定确定可复现。但 `subject` 未绑定，记录层的完整性也不完整。
4. **商业价值 58.8/100**（第一阶段 59.0），"问题真实性"与"差异度"仍是 3–3.5 分的低位，卡点不在叙事，在能力。

## 8. 下一阶段可选路线（按可行性排序）

1. **定位收缩为"可核验存证层"**：与检测解耦，输入接**已归一化的告警**（Splunk/Sentinel/Wazuh 导出的告警对象），只负责"结论 + 凭证 + 可独立复核"。这条路线与本次实测结论一致，且不需要自建检测能力；配套必须补齐 `subject` 绑定。
